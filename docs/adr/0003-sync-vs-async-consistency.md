# ADR-0003 跨服务一致性优先最终一致，Seata 为兜底

- 状态：已采纳
- 日期：2026-09-18
- 决策人：@architect

## 背景

`order-service` 创建订单需要扣减 `inventory-service` 库存。若用两张库，存在一致性风险。团队第一反应是"上 Seata"。

## 可选方案

A. 全部跨服务写操作都用 Seata AT
B. 默认 MQ + Outbox 最终一致；仅少量强一致场景用 Seata
C. 不用分布式事务，靠定时对账补偿

## 决策

选 **B**。

## 理由

- Seata AT 会持有全局锁，长事务下吞吐下降明显；我们的大多数场景（发货通知、积分、搜索同步）业务上能接受秒级延迟。
- 只有"创建订单 + 扣库存"需要强一致（用户立刻看到订单成功但库存没扣 = 超卖）。
- C 被否：对账窗口内会超卖，业务不接受。
- A 被否：为 5% 的场景给 100% 的服务加全局锁成本。

## 后果

- 正面：大部分链路不引入额外中间件依赖；故障面小。
- 负面：需要自建**可靠事件表（Outbox）**，增加一张表和一次同事务写入；消费者必须幂等。
- 后续：
  1. `sql/outbox.sql` 模板
  2. 使用 Seata 时必须写 ADR 说明
  3. `undo_log` 建表加入新服务上线检查清单
